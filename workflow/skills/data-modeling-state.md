# 数据建模与状态管理

> **使用场景**：设计数据架构、选择缓存策略、处理分布式一致性、构建状态机、评估读写分离方案时加载本 skill

## 第一性原理

> **数据建模的本质**：在满足一致性、可用性和性能约束下，选择能准确表达业务语义、支撑高效查询、并能随业务演化的数据结构。

## 状态建模方法论

### 状态 vs 事件

| 概念 | 定义 | 适用场景 |
|------|------|---------|
| **状态（State）** | 某一时刻的快照 | CRUD 应用、配置管理 |
| **事件（Event）** | 状态变更的记录 | 审计追踪、事件溯源、CQRS |
| **命令（Command）** | 意图的表达 | 用户操作、系统指令 |

**核心问题**：你的业务需要"知道现在是什么"还是"知道怎么变成现在的"？

- 只需要当前状态 → 状态建模
- 需要历史 + 当前 → 事件溯源（Event Sourcing）
- 读多写少且读模型多样 → CQRS + 事件溯源

### 状态生命周期建模

```
业务实体状态生命周期：

  [初始] → [激活] → [过期/归档]
     ↓        ↓
  创建事件   状态转换事件
```

**规则**：每个业务实体必须有明确的状态机定义。状态转换必须单向（避免循环状态），除非业务本身允许（如订单的取消→重新下单）。

## 状态机设计

### 有限状态机（FSM）设计原则

| 原则 | 说明 | 违反后果 |
|------|------|---------|
| **状态穷尽** | 所有可能状态都被定义 | 未定义状态导致无法处理 |
| **转换明确** | 每个状态允许的转换被显式定义 | 非法转换导致数据不一致 |
| **单一状态** | 实体在任一时刻只有一个状态 | 并发修改导致状态冲突 |
| **转换原子** | 状态转换是原子操作 | 中间状态暴露导致竞态条件 |

### 状态转换表模板

```markdown
| 当前状态 | 允许事件 | 目标状态 | 前置条件 | 副作用 |
|---------|---------|---------|---------|--------|
| PENDING | PAYMENT_RECEIVED | PAID | 金额 > 0 | 发送确认邮件 |
| PAID    | SHIP             | SHIPPED | 库存充足 | 扣减库存 |
| SHIPPED | DELIVER          | DELIVERED | 物流签收 | 更新物流状态 |
| *       | CANCEL           | CANCELLED | 未发货 | 退款处理 |
```

**规则**：状态转换表中必须包含"*"（通配）行处理取消/异常路径。不要只在"正常流程"中定义状态机。

### 并发状态冲突解决

| 策略 | 实现 | 适用 |
|------|------|------|
| **乐观锁（版本号）** | 更新时检查版本号 | 冲突率低（< 5%） |
| **悲观锁** | 读取时锁定记录 | 冲突率高或关键资源 |
| **状态机验证** | 数据库 CHECK 约束 | 所有场景（兜底） |
| **事件日志冲突检测** | 比较事件时间戳 | 事件溯源架构 |

## 缓存策略决策矩阵

### 缓存模式选择

| 模式 | 读流程 | 写流程 | 一致性 | 复杂度 | 适用 |
|------|--------|--------|--------|--------|------|
| **Cache-Aside** | 先读缓存，miss 读 DB 回填 | 写 DB，删缓存 | 最终一致 | 低 | 通用场景 |
| **Read-Through** | 读缓存，miss 由缓存层读 DB | 写 DB，删缓存 | 最终一致 | 中 | 缓存中间件（Redis） |
| **Write-Through** | 读缓存 | 写缓存，同步写 DB | 强一致 | 中 | 写频繁且一致性要求高 |
| **Write-Behind** | 读缓存 | 写缓存，异步写 DB | 可能丢失 | 高 | 写极高吞吐量 |
| **Refresh-Ahead** | 缓存提前刷新 | 直接写 DB | 最终一致 | 高 | 可预测访问模式 |

### Cache-Aside 经典实现

```
读：
1. 读缓存 key
2. 命中 → 返回
3. 未命中 → 读 DB → 写入缓存 → 返回

写：
1. 更新 DB
2. 删除缓存（不是更新缓存）
```

**Why delete instead of update?**
- 并发写场景：两个更新同时发生，缓存更新的顺序可能与 DB 不一致
- 删除缓存强制下次读时从 DB 回填，保证一致性
- 代价：一次 cache miss

### 缓存一致性陷阱

| 陷阱 | 场景 | 解决方案 |
|------|------|---------|
| **缓存穿透** | 查询不存在的数据，每次都命中 DB | Bloom Filter 或空值缓存 |
| **缓存击穿** | 热点 key 过期，大量并发请求直达 DB | 互斥锁重建 + 逻辑过期 |
| **缓存雪崩** | 大量 key 同时过期 | 过期时间加随机偏移 |
| **双写不一致** | 写 DB 成功但删缓存失败 | 消息队列异步补偿 + 设置短过期时间 |

## 一致性模型选择

### CAP 定理实践

> 在分区发生时，你只能选择一致性（C）或可用性（A），不能同时保证。

| 场景 | 选择 | 理由 |
|------|------|------|
| 金融交易 | CP | 数据正确性优先于可用性 |
| 社交媒体 feed | AP | 短暂的不一致可接受 |
| 电商库存 | 可配置 | 下单用 CP，浏览用 AP |
| 配置管理 | CP | 配置不一致会导致行为不可预测 |

### 一致性级别

| 级别 | 定义 | 实现 | 性能 |
|------|------|------|------|
| **强一致性** | 所有读取看到最新写入 | 2PC、Paxos、Raft | 低 |
| **顺序一致性** | 所有进程看到相同的操作顺序 | 全局时钟/向量时钟 | 中 |
| **因果一致性** | 因果相关的操作顺序一致 | 向量时钟、Lamport 时间戳 | 中 |
| **最终一致性** | 没有新写入后，所有读取收敛到相同值 | 异步复制、CRDT | 高 |

### 选择流程

```
业务是否允许短暂不一致？
    ├── 否 → 强一致性（2PC/Raft）
    └── 是 → 数据是否有因果关系？
                ├── 是 → 因果一致性
                └── 否 → 最终一致性（性能最优）
```

## 数据分区与分片

### 分片策略

| 策略 | 分片键 | 优点 | 缺点 |
|------|--------|------|------|
| **哈希分片** | hash(key) % N | 均匀分布 | 扩缩容复杂（需 rehash） |
| **范围分片** | 时间范围 / ID 范围 | 范围查询高效 | 热点（最新数据集中） |
| **列表分片** | 预定义映射 | 灵活 | 需人工维护映射 |
| **复合分片** | 哈希 + 范围 | 兼顾均匀和范围 | 复杂度高 |

### 分片路由

```sql
-- 一致性哈希：扩容时只需迁移少量数据
shard = consistent_hash(user_id, virtual_nodes=150)
```

**规则**：
- 分片键选择：高基数字段（避免热点），且是查询条件中频率最高的字段
- 预留虚节点（virtual nodes）：一致性哈希中每个物理节点映射到多个虚节点，使数据分布更均匀
- 分片数量建议：初始 N × 2（预留扩容空间）

## 事件溯源（Event Sourcing）

### 核心概念

```
传统模型：            事件溯源模型：
┌─────────┐          ┌─────────┐    ┌─────────┐
│  当前状态  │    →    │ 事件流   │ → │ 投影状态  │
└─────────┘          └─────────┘    └─────────┘
                     Event Store     Read Model
```

### 何时使用事件溯源

| 条件 | 是否适用 |
|------|---------|
| 需要完整的审计日志 | ✅ 必须使用 |
| 读模型需要多种形态 | ✅ 推荐使用 |
| 需要时间旅行（回到任意时刻状态） | ✅ 必须使用 |
| 简单 CRUD | ❌ 过度工程 |
| 团队没有事件驱动经验 | ❌ 学习成本高 |

### 事件溯源挑战

| 挑战 | 解决方案 |
|------|---------|
| **事件 schema 演化** | 事件版本号 + 向上兼容读取 |
| **投影延迟** | 明确最终一致性的时间窗口 |
| **事件存储增长** | 快照（Snapshot）+ 归档 |
| **全局顺序保证** | 单分区顺序 / 向量时钟 |

## 反模式

| 反模式 | 症状 | 修复 |
|--------|------|------|
| **上帝对象** | 一个表包含 50+ 字段 | 按职责拆分（用户基本信息、用户偏好、用户统计） |
| **缓存一切** | 所有数据都进缓存，DB 成摆设 | 只缓存热点数据（通常是 20% 数据满足 80% 查询） |
| **忽略 TTL** | 缓存永不过期，内存泄漏 | 所有缓存必须设置合理的 TTL |
| **数据库即队列** | 用 DB 表做任务队列 | 使用真正的消息队列（Kafka/RabbitMQ） |
| **分布式事务滥用** | 用 2PC 处理所有跨服务写 | 最终一致性 + 补偿事务（Saga） |
| **无版本的状态机** | 状态转换逻辑硬编码，无法变更 | 状态转换规则外置（配置/数据库），支持热更新 |

## Rules

1. **Choose cache strategy based on read/write ratio** — 读:写 > 10:1 用 Cache-Aside；读:写 < 3:1 考虑 Write-Through 或不用缓存。

2. **All cached data must have TTL** — 没有 TTL 的缓存是内存泄漏。基础数据 TTL = 1小时，热点数据 TTL = 5-15分钟，配置数据 TTL = 24小时。

3. **Never use cache as source of truth for financial data** — 缓存中的金额、余额、库存数据永远只是 DB 的副本。任何计算必须在 DB 层完成。

4. **State transitions must be validated at the database layer** — 状态机校验不能只在前端/应用层。数据库必须有 CHECK 约束或触发器保证状态转换合法性。

5. **Event sourcing is not for simple CRUD** — 事件溯源增加 3-5 倍复杂度。只有需要审计、时间旅行或多读模型时才使用。

6. **Shard key must have high cardinality** — 低基数的分片键（如"性别"只有 2 个值）会导致极端热点。分片键的有效基数应 > 1000。

7. **Prefer eventual consistency for cross-service writes** — 跨服务写操作避免分布式事务（2PC）。使用 Saga 模式：本地事务 + 补偿 + 最终一致。

## SOP

1. **Phase 1: Data Access Pattern Analysis** — 分析查询模式：读多写少？范围查询？点查？聚合？连接？写操作频率？

2. **Phase 2: Consistency Requirement Clarification** — 明确每个数据实体的一致性要求：强一致？最终一致？可接受的最大不一致窗口？

3. **Phase 3: State Machine Design** — 为有生命周期的实体设计状态机：定义所有状态、允许的转换、前置条件、副作用。

4. **Phase 4: Cache Strategy Selection** — 根据读写比、一致性要求、数据更新频率选择缓存模式并配置 TTL。

5. **Phase 5: Partitioning Design** — 如果数据量 > 1000万行或增长 > 100万行/月，设计分片策略。选择分片键，计算虚节点数。

6. **Phase 6: Event Sourcing Evaluation** — 判断是否需要事件溯源：需要审计？时间旅行？多读模型？如果不需要，使用传统状态模型。

7. **Phase 7: Concurrency Control** — 为每个写操作选择并发控制策略：乐观锁（版本号）或悲观锁。冲突率高（>10%）时用悲观锁。

## Best Practices

1. **Model time explicitly** — 不要依赖"现在"这个隐式时间。所有时间相关操作使用显式时间戳参数。支持时间旅行查询和历史状态重建。

2. **Use immutable data structures where possible** — 不可变数据结构（value objects）消除一类并发 bug（修改时无需加锁），并天然支持审计。

3. **Design the query path first** — 不要先设计表结构再考虑查询。列出系统中最频繁/最重要的 5 个查询，确保数据模型能高效支持它们。

4. **Keep aggregates small** — DDD 聚合根应该很小（< 1000 行）。大的聚合根导致并发冲突率高、加载慢、难以理解。

5. **Version your events and schemas** — 事件溯源中的事件必须有版本号。读取时根据版本号应用对应的反序列化逻辑，支持 schema 演化。

6. **Cache warming for predictable hot data** — 对已知的热点数据（如首页推荐、热门商品），在应用启动时预热缓存，避免冷启动时的 cache miss 风暴。

## Gotchas

1. **Read-your-own-writes inconsistency** — 用户写入后立即读取，可能在最终一致性架构中读到旧数据。解决方案：写操作后的短时间窗口内（如 5 秒），读请求路由到主节点。

2. **Cache stampede on cold start** — 应用重启后缓存为空，大量并发请求同时 miss 并查询 DB。解决方案：启动时预热缓存，或使用互斥锁控制并发重建。

3. **Event sourcing replay performance** — 重建聚合状态时重放所有历史事件可能很慢。解决方案：定期快照（每 N 个事件），重放时从最新快照开始。

4. **Clock skew in distributed timestamps** — 不同节点的系统时间不一致可能导致事件顺序错乱。解决方案：使用逻辑时钟（Lamport/向量时钟）而非物理时间戳。

5. **Soft delete vs hard delete** — 软删除（标记删除）保留数据但增加查询复杂度；硬删除节省空间但无法恢复。选择依据：法规要求？恢复需求？数据量？

## Context Hints

1. **Data outlives code** — 数据比代码存活更久。设计数据模型时考虑 5 年后的演化。不要用当前业务的临时需求来约束长期数据结构。

2. **Consistency is a spectrum, not a binary choice** — 强一致性和最终一致性之间有很多中间选项（因果一致性、会话一致性、单调读）。选择最适合业务需求的级别。

3. **The database is not a queue** — 关系型数据库不是为队列语义设计的。用 DB 表做任务队列会导致性能问题（行锁竞争、慢查询）。使用专用消息队列。

4. **Normalization is for writes, denormalization is for reads** — 写路径追求规范化（减少冗余、保证一致性），读路径追求反规范化（减少连接、提升性能）。CQRS 将这个原则推到极致：写模型规范，读模型反规范。

5. **State machines make implicit logic explicit** — 将业务规则编码为状态转换表，比散落在 if/else 中的逻辑更容易理解、测试和维护。
