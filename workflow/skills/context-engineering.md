# 上下文工程

> **使用场景**：管理LLM上下文窗口、决定保留/丢弃/压缩哪些内容、设计多轮对话状态、优化Token使用时加载本 skill

## 第一性原理

> **上下文工程的本质**：在有限的Token预算内，选择最能提升模型输出质量的信息子集。不是"塞满所有东西"，而是"只放能改变决策的内容"。

---

## 上下文层级模型

### L0-L3 四层架构

| 层级 | 内容 | 优先级 | 压缩策略 |
|------|------|--------|---------|
| **L0: 系统指令** | 角色定义、任务指令、输出格式 | 永不丢弃 | 无压缩 |
| **L1: 核心上下文** | 当前任务相关代码、需求、关键决策 | 高优先级 | 最小压缩 |
| **L2: 支撑上下文** | 相关技能、经验、架构约束 | 中优先级 | 中度压缩 |
| **L3: 通用上下文** | 项目画像、代码图谱、历史对话 | 低优先级 | 最大压缩或丢弃 |

### Token 预算分配公式

```
总预算 = CONTEXT_WINDOW_MAX - RESERVE（保留10%给输出）

L0 = base_cost（固定）
L1 = min(核心内容实际tokens, 总预算 × 40%)
L2 = min(支撑内容实际tokens, 总预算 × 30%)
L3 = 剩余预算

如果 L0 + L1 > 总预算 × 60%：
    发出警告：核心内容过多，建议分批处理
```

## 上下文相关性评分

### 评分维度

| 维度 | 权重 | 评估方法 |
|------|------|---------|
| **语义相似度** | 40% | 当前任务描述 vs 上下文内容的 embedding 相似度 |
| **符号关联** | 25% | 上下文中的符号是否出现在当前任务的代码路径中 |
| **时间衰减** | 15% | 越久远的上下文相关性越低（指数衰减） |
| **任务类型匹配** | 10% | 上下文所属技能域是否与当前任务匹配 |
| **用户显式引用** | 10% | 用户是否主动提及该上下文 |

### 相关性排序流程

```
1. 计算每个上下文块的综合得分
2. 按得分降序排序
3. 从高分开始累加，直到接近预算上限
4. 低分块进入压缩或丢弃队列
```

## 压缩策略

### 三层压缩管线

| 层级 | 技术 | 压缩比 | 适用 |
|------|------|--------|------|
| **L1: 结构化压缩** | 摘要提取、关键信息抽取 | 30-50% | 长文档、代码文件 |
| **L2: 语义压缩** | Embedding 降维、聚类去重 | 50-70% | 大量相似上下文 |
| **L3: 激进压缩** | 仅保留符号签名、删除实现细节 | 70-90% | 极端预算不足 |

### 代码上下文压缩

| 原始内容 | 压缩后 | 保留的信息 |
|---------|--------|-----------|
| 完整函数实现 | 函数签名 + 关键注释 | 接口契约、副作用 |
| 完整类定义 | 类名 + 公共方法签名 | 职责、依赖关系 |
| 完整文件 | 文件路径 + 导出符号列表 | 模块结构 |
| 测试用例 | 测试名 + 断言类型 | 验证范围 |

### 压缩决策树

```
Token 使用率 > 80%？
    ├── 是 → 触发 L1 压缩（结构化摘要）
    │           └── Token 使用率仍 > 85%？
    │                   ├── 是 → 触发 L2 压缩（语义去重）
    │                   │           └── Token 使用率仍 > 90%？
    │                   │                   ├── 是 → 触发 L3 压缩（激进截断）
    │                   │                   └── 否 → 维持 L2
    │                   └── 否 → 维持 L1
    └── 否 → 不压缩，维持原始内容
```

## 多轮对话状态管理

### 对话状态持久化

| 状态类型 | 内容 | 持久化策略 |
|---------|------|-----------|
| **任务上下文** | 当前目标、进度、决策 | 必须持久化（不丢失） |
| **代码上下文** | 引用文件、修改位置 | 按需加载（不持久化全量） |
| **用户偏好** | 编码风格、输出偏好 | 跨会话持久化（配置/经验） |
| **临时计算** | 中间结果、草稿 | 不持久化（重新生成） |

### 对话轮次优化

```
长对话截断策略：

保留：
- 第 1 轮（初始需求，永不丢弃）
- 最近 3 轮（工作记忆，高优先级）
- 包含关键决策的轮次（ADR、架构决策）
- 用户纠正的轮次（错误修正记录）

压缩：
- 中间轮次的实现细节（代码已写入文件，无需保留全文）
- 已解决的问答（保留结论，丢弃过程）

丢弃：
- 纯寒暄/确认轮次
- 已过时且未被引用的中间结果
```

## 上下文注入策略

### 技能匹配注入

```
任务关键词提取 → 技能库匹配 → 相关性排序 → 注入 Top-N

注入上限：
- 单个技能最大 tokens: 1500
- 总技能注入 tokens: 2800（MAX_INJECT_TOKENS）
- 技能数量: 3-5 个（避免信息过载）
```

### 经验注入

| 经验类型 | 触发条件 | 注入方式 |
|---------|---------|---------|
| **项目经验** | 匹配当前文件路径/模块 | 前置注入（高优先级） |
| **领域经验** | 匹配任务类型/技术栈 | 按需注入 |
| **错误经验** | 当前任务与历史错误模式匹配 | 警告式注入 |

## 反模式

| 反模式 | 症状 | 修复 |
|--------|------|------|
| **上下文堆砌** | 所有历史对话、所有文件全部塞入 | 相关性评分 + 分层过滤 |
| **过早丢弃** | 一超过预算就粗暴截断 | 渐进式压缩（L1→L2→L3） |
| **静态预算** | 所有任务分配相同上下文大小 | 动态预算分配（基于任务复杂度） |
| **忽略用户显式引用** | 用户明确提及的内容被压缩丢弃 | 用户引用内容自动标记 L0 优先级 |
| **技能过载** | 注入 10+ 个技能导致模型困惑 | 限制技能数量（3-5 个），按相关性排序 |
| **对话状态膨胀** | 多轮后上下文无限增长 | 定期总结（每 5 轮生成一次对话摘要） |

## Rules

1. **Token budget is a hard constraint, not a guideline** — 超出上下文窗口不会"勉强处理"，而是会导致内容被截断或请求失败。必须主动管理。

2. **Relevance trumps completeness** — 1000 tokens 高度相关的上下文 > 3000 tokens 低相关上下文。宁可少而精，不要多而杂。

3. **Compress before discard** — 优先使用 L1/L2 压缩保留信息的结构，而不是直接丢弃。只有在压缩后仍超预算时才丢弃。

4. **User-explicit references are L0 priority** — 用户主动提及的文件、概念、决策必须完整保留，不受压缩/丢弃策略影响。

5. **Summarize long conversations every 5 rounds** — 超过 5 轮的对话必须生成摘要，后续轮次基于摘要而非完整历史。摘要是压缩后的"工作记忆"。

6. **Skill injection must not exceed MAX_INJECT_TOKENS** — 技能注入是上下文最大的消耗来源之一。必须严格限制在 2800 tokens 以内，并按相关性排序取舍。

7. **Never pass raw content between stages** — 阶段间传递应使用文件路径引用，而非原始内容。这既是上下文工程（节省 tokens），也是架构设计（松耦合）。

## SOP

1. **Phase 1: Token Audit** — 评估当前任务的 Token 需求：估算代码量、文档量、对话历史。确定总预算。

2. **Phase 2: Content Inventory** — 列出所有可用的上下文来源：技能、经验、代码文件、历史对话、项目画像。为每个来源计算相关性得分。

3. **Phase 3: Layer Allocation** — 按 L0→L1→L2→L3 顺序分配预算。L0 固定，L1 优先满足，L2/L3 填入剩余空间。

4. **Phase 4: Compression Pipeline** — 如果总内容 > 预算，按 L1→L2→L3 压缩策略逐层压缩，直到满足预算。

5. **Phase 5: Quality Check** — 确认高优先级内容（用户引用、关键决策）未被压缩/丢弃。验证上下文的完整性。

6. **Phase 6: Execution** — 基于优化后的上下文执行任务。监控实际 Token 使用量，为下一轮优化提供数据。

7. **Phase 7: Session Summary** — 任务完成后生成对话摘要。记录哪些上下文被使用了、哪些被丢弃了、丢弃是否影响了质量。

## Checklist

### Token 预算
- [ ] 总预算已计算（含输出预留）
- [ ] L0-L3 层级已分配
- [ ] 实际使用量 < 预算 × 90%

### 相关性
- [ ] 所有上下文块已评分排序
- [ ] 用户显式引用内容已标记 L0
- [ ] 低相关性内容已压缩或丢弃

### 压缩质量
- [ ] 压缩后仍保留关键信息
- [ ] 接口契约未丢失
- [ ] 决策上下文未丢失

### 状态管理
- [ ] 多轮对话有摘要机制
- [ ] 关键决策持久化
- [ ] 临时内容未污染长期状态

## Best Practices

1. **Use "file path references" instead of "raw content passing"** — 阶段间和 Agent 间传递文件路径而非内容。这是上下文工程的核心原则：延迟加载、按需读取。

2. **Create a "context heat map" for complex tasks** — 对复杂任务，维护一个"上下文热力图"：哪些文件/知识被引用了多少次。高频内容优先保留。

3. **Implement progressive disclosure in prompts** — 不要把所有细节放在第一层。先给概览，模型需要时再提供详细内容。减少初始上下文的噪音。

4. **Use structured formats (JSON, tables) over prose for context** — 结构化格式信息密度更高（tokens/信息量比更优）。表格、列表、键值对比段落更高效。

5. **Version your context schemas** — 上下文注入的内容应有版本标识。当上下文格式变更时，确保模型能正确解析新旧混合的上下文。

6. **Measure context-to-output quality correlation** — 跟踪不同上下文策略下的输出质量。数据驱动的上下文优化比直觉更可靠。

## Gotchas

1. **Context window != working memory** — 模型虽然能"看到" 200K tokens，但对长距离依赖的注意力会衰减。最关键的信息应放在 prompt 的前面和后面（首因效应和近因效应）。

2. **Compression loses nuance** — 过度压缩会丢失微妙的约束条件（如"除非 X 否则不要 Y"）。压缩后必须验证关键约束是否保留。

3. **Recursive context inflation** — 如果模型输出被重复注入上下文（如 chain-of-thought 的推理过程），tokens 会指数增长。定期截断或总结推理链。

4. **Skill injection order matters** — 同一主题的不同技能可能有冲突建议。注入顺序影响模型的倾向性。高优先级技能应放在后面（近因效应）。

5. **Stale context is worse than no context** — 过时的上下文（如已重构的代码、已变更的架构决策）会引导模型做出错误决策。上下文必须有新鲜度标记。

## Context Hints

1. **"The best context is the context you don't need"** — 如果系统架构清晰、代码自解释、接口契约明确，模型需要的上下文就少。上下文工程的上游是架构质量和代码可读性。

2. **Context is a liability, not just an asset** — 每增加一个上下文块，就增加了噪声和矛盾的可能性。只有"能改变模型输出"的上下文才值得注入。

3. **LLMs are stateless — context engineering IS the state management** — 模型本身无状态。所有"记忆"都通过上下文注入实现。上下文工程就是状态管理工程。

4. **Token cost is both literal and figurative** — 字面成本（API 费用）和 figurative 成本（模型注意力分散、推理质量下降）都需要考虑。有时"省 token"就是"提升质量"。

5. **The "attention bottleneck" is real** — 即使上下文窗口很大，模型的"注意力带宽"有限。不要假设模型会注意到你放在中间的微妙提示。关键信息必须前置或重复。
