# 弹性工程

> **使用场景**：设计容错机制、处理第三方依赖故障、预防级联故障、评估系统可靠性时加载本 skill

## 第一性原理

> **弹性工程的本质**：承认故障是不可避免的，通过设计让系统在故障发生时优雅降级而非全面崩溃，并快速自愈。

---

## SLA / SLO / SLI 框架

在讨论弹性之前，必须先定义"可用"的标准。

| 术语 | 定义 | 示例 |
|------|------|------|
| **SLI（服务水平指标）** | 可量化的服务质量指标 | "订单服务的 p99 延迟" |
| **SLO（服务水平目标）** | SLI 的目标值 | "p99 延迟 < 200ms" |
| **SLA（服务水平协议）** | SLO + 违约后果 | "p99 延迟 < 200ms，否则退款" |

### 错误预算（Error Budget）

```
错误预算 = 1 - SLO（如 SLO=99.9%，则错误预算=0.1%）

每月允许的故障时间 = 错误预算 × 30天 × 24小时
  99.9% SLO = 43.2 分钟/月
  99.99% SLO = 4.32 分钟/月
  99.999% SLO = 26 秒/月
```

**规则**：
- 当错误预算消耗 > 50% 时：冻结非紧急发布
- 当错误预算消耗 > 75% 时：所有新功能发布暂停，专注稳定性修复
- 当错误预算消耗 > 90% 时：进入"救火模式"，仅允许 hotfix

### SLO 设计原则

| 原则 | 说明 |
|------|------|
| **可测量** | SLI 必须能从监控数据直接计算 |
| **可达成** | SLO 必须基于历史数据，而非愿望 |
| **有意义** | SLO 必须反映用户体验，而非系统内部指标 |
| **分层** | 每个服务有独立 SLO，用户旅程有聚合 SLO |

## 故障分类与应对策略

| 故障类型 | 特征 | 典型应对 |
|---------|------|---------|
| **瞬时故障** | 短暂、自恢复（网络抖动、GC pause） | 重试 + 退避 |
| **持续故障** | 持续、需人工介入（服务宕机、DB 崩溃） | 熔断 + 降级 |
| ** byzantine 故障** | 表现不一致（数据损坏、时钟错乱） | 冗余校验 + 隔离 |
| **级联故障** | A 故障 → B 过载 → C 崩溃 | 背压 + 隔离舱 |
| **灰度故障** | 部分异常、部分正常（慢节点、部分分片损坏） | 健康探测 + 自动剔除 |

### Gray Failure（灰度故障）识别

灰度故障是最难发现的故障类型 — 服务部分可用但性能退化。

| 信号 | 检测方法 | 误判风险 |
|------|---------|---------|
| 单个节点 p99 延迟异常 | 节点级 latency 分布对比 | 低（需节点级监控） |
| 部分请求超时 | 超时率 vs 错误率分离分析 | 低 |
| 健康检查通过但业务失败 | 深度健康检查（探针真实业务路径） | 中（增加探针开销） |
| 负载均衡后某些后端响应慢 | 后端级 metrics 对比 | 低 |

**规则**：健康检查不应该只检查"进程存活"，应该探测真实的业务路径（如执行一个轻量级查询）。

## 重试策略决策矩阵

**重试是把双刃剑** — 错误的重试会加剧故障（重试风暴）。

### 何时重试

| 场景 | 是否重试 | 理由 |
|------|---------|------|
| 网络超时（Timeout） | ✅ 是 | 可能是瞬时网络抖动 |
| 连接拒绝（Connection Refused） | ❌ 否 | 服务确实不可用，重试无益 |
| 5xx 服务器错误 | ⚠️ 视情况 | 如果是负载过高，重试会加剧 |
| 429 Too Many Requests | ⚠️ 视情况 | 需要退避，但不要无限重试 |
| 4xx 客户端错误 | ❌ 否 | 请求本身有问题，重试会变本加厉 |

### 退避策略选择

| 策略 | 公式 | 适用场景 | 风险 |
|------|------|---------|------|
| **固定间隔** | delay = base | 故障持续时间已知 | 无抖动，可能同步重试 |
| **线性退避** | delay = base * attempt | 故障恢复时间线性 | 重试频率仍较高 |
| **指数退避** | delay = min(base * 2^n, cap) | 通用场景，最推荐 | 上限后无区别 |
| **指数退避 + 抖动** | delay = min(base * 2^n, cap) * (1 + random) | **生产环境首选** | 最复杂，防止同步 |

**规则**：
- 最大重试次数 ≤ 3 次
- 总重试时间 < 请求超时时间
- **必须设置重试上限**（circuit breaker）

### 请求对冲（Request Hedging）

当某个服务有多个副本时，向多个副本同时发送请求，取第一个成功的响应。

```
对冲条件：
1. 服务有 ≥3 个健康副本
2. 请求是幂等的（idempotent）
3. 第 1 个请求的延迟 > p95 基线
4. 向第 2 个副本发送对冲请求

取消条件：任一请求成功 → 立即取消其他请求
```

**风险**：2x 瞬时负载。使用条件：服务的资源余量 > 50%。

## 熔断器（Circuit Breaker）

### 三态模型

```
        ┌─────────────┐
        │   CLOSED    │ ← 正常状态，请求通过
        │  (健康)      │
        └──────┬──────┘
               │ 错误率超过阈值
               ▼
        ┌─────────────┐
        │    OPEN     │ ← 熔断状态，请求快速失败
        │  (熔断)     │
        └──────┬──────┘
               │ 超时后
               ▼
        ┌─────────────┐
        │ HALF-OPEN   │ ← 试探状态，允许少量请求
        │  (探测)     │
        └─────────────┘
```

### 配置参数

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 失败阈值 | 50%-70% | 连续请求中失败比例超过此值触发熔断 |
| 窗口大小 | 10-100 请求 | 计算失败率的滑动窗口 |
| 熔断持续时间 | 10-60 秒 | OPEN 状态的持续时间 |
| 半开试探数 | 1-5 请求 | HALF-OPEN 状态允许的请求数 |

**规则**：熔断器必须配合降级策略。熔断后返回什么？缓存？默认值？排队？

## 降级策略

当依赖不可用时，系统的应对方式：

| 策略 | 实现方式 | 用户体验 | 适用场景 |
|------|---------|---------|---------|
| **静态降级** | 返回预置默认值 | 功能受限但可用 | 非核心数据（推荐、广告） |
| **缓存降级** | 返回缓存数据（可能过期） | 数据可能旧 | 读多写少（商品详情、用户信息） |
| **简化降级** | 返回简化版响应 | 核心功能可用 | 功能丰富度可妥协（富文本 → 纯文本） |
| **异步降级** | 接受请求，异步处理 | 延迟响应 | 非实时需求（邮件、报表） |
| **拒绝降级** | 快速失败，提示用户 | 功能不可用 | 核心依赖完全不可用时 |

**选择矩阵**：

```
数据新鲜度要求高？
    ├── 是 → 能否接受简化？
    │           ├── 是 → 简化降级
    │           └── 否 → 拒绝降级
    └── 否 → 有缓存？
                ├── 是 → 缓存降级
                └── 否 → 静态降级
```

## 负载丢弃（Load Shedding）

当系统过载时，有策略地丢弃部分请求以保护核心功能。

### 丢弃策略

| 策略 | 实现 | 适用场景 |
|------|------|---------|
| **优先级丢弃** | 丢弃低优先级请求（非核心功能） | 电商大促期间 |
| **百分比丢弃** | 随机丢弃 X% 的请求 | 均匀负载场景 |
| **队列丢弃** | 丢弃队列中等待时间最长的请求 | 请求类型差异大 |
| **资源感知丢弃** | 当 CPU/内存 > 阈值时开始丢弃 | 自适应保护 |

### 丢弃决策树

```
CPU > 80% 或 队列深度 > 100？
    ├── 是 → 丢弃优先级 < P2 的请求
    │           └── CPU > 90%？
    │                   ├── 是 → 丢弃优先级 < P1 的请求（仅保留核心功能）
    │                   └── 否 → 继续监控
    └── 否 → 正常处理
```

**规则**：负载丢弃必须配合客户端重试（带退避）。被丢弃的请求应该返回 503 + Retry-After header。

## 隔离模式

### 隔离舱（Bulkhead）

限制故障传播范围：

| 隔离维度 | 实现方式 | 保护效果 |
|---------|---------|---------|
| **线程池隔离** | 关键路径独立线程池 | 非关键路径拖垮不影响关键路径 |
| **连接池隔离** | 每个依赖独立连接池 | 一个依赖的连接耗尽不影响其他 |
| **服务实例隔离** | 关键功能独占实例 | 非关键功能的高负载不影响核心 |

**规则**：关键路径（用户支付、下单）必须与辅助路径（日志、统计）资源隔离。

### 限流（Rate Limiting）

| 算法 | 特点 | 适用 |
|------|------|------|
| **令牌桶** | 允许突发，平滑平均速率 | API 限流 |
| **滑动窗口** | 精确计数，无突发 | 严格配额场景 |
| **漏桶** | 严格匀速，无突发 | 出站流量整形 |

## 级联故障预防

### 死亡螺旋识别

级联故障的典型模式：

```
1. 服务 A 变慢（依赖响应延迟 / CPU 饱和）
2. 调用 A 的服务 B 线程池耗尽（等待 A 响应）
3. B 开始超时，客户端重试 → A 负载进一步增加
4. A 完全不可用 → 依赖 A 的所有服务都失败
5. 整个系统雪崩
```

### 防御措施

| 防线 | 措施 | 实施点 |
|------|------|--------|
| **第一线：超时** | 设置合理的请求超时 | 每个外部调用 |
| **第二线：限流** | 限制入口流量 | API Gateway / 负载均衡 |
| **第三线：熔断** | 快速失败不健康依赖 | 客户端调用层 |
| **第四线：降级** | 依赖不可用时优雅降级 | 业务逻辑层 |
| **第五线：隔离** | 资源池分离 | 线程/连接池配置 |
| **第六线：负载丢弃** | 过载时保护核心 | 入口网关层 |

## 多区域灾备与容灾

### RTO / RPO 定义

| 指标 | 定义 | 典型要求 |
|------|------|---------|
| **RTO（恢复时间目标）** | 故障发生后，系统恢复服务的最长时间 | 核心系统 < 15 分钟 |
| **RPO（恢复点目标）** | 故障发生后，可接受的数据丢失量 | 金融系统 < 1 分钟 |

### 灾备架构模式

| 模式 | RTO | RPO | 成本 | 适用 |
|------|-----|-----|------|------|
| **备份恢复** | 小时级 | 天级 | 低 | 非核心数据 |
| **温备（Warm Standby）** | 分钟级 | 分钟级 | 中 | 核心业务 |
| **热备（Hot Standby）** | 秒级 | 接近0 | 高 | 支付、交易 |
| **多活（Active-Active）** | 0（自动切换） | 0 | 最高 | 全球服务 |

### 数据一致性策略

| 场景 | 策略 | 一致性保证 |
|------|------|-----------|
| 同城双活 | 同步复制 | 强一致性 |
| 异地多活 | 异步复制 + 冲突检测 | 最终一致 + 冲突解决 |
| 读多写少 | 写主读从 | 写强一致，读最终一致 |

## 混沌工程（Chaos Engineering）

### 混沌实验 SOP

```
1. 定义稳态假设："在正常情况下，服务的 p99 延迟 < 200ms"
2. 设计故障注入：随机 kill 10% 的依赖服务实例
3. 执行实验：在生产环境（或准生产）注入故障
4. 观察偏离：p99 延迟是否超过 200ms？降级是否触发？
5. 修复差距：如果偏离，修复系统后再重复实验
6. 自动化：将验证通过的实验加入 CI pipeline
```

### 混沌实验类型

| 实验 | 注入方式 | 验证目标 |
|------|---------|---------|
| **实例终止** | 随机 kill Pod/进程 | 自动恢复、重新调度 |
| **网络延迟** | 增加 100-500ms 延迟 | 超时配置、降级策略 |
| **丢包** | 随机丢弃 1-5% 数据包 | 重试策略、幂等性 |
| **CPU 饱和** | 占用 90%+ CPU | 负载丢弃、自动扩容 |
| **内存压力** | 占用 90%+ 内存 | OOM 处理、优雅退出 |
| **时钟偏移** | 调整系统时间 | 分布式锁、超时逻辑 |

### 混沌工程原则

1. **最小化爆炸半径** — 先从小规模、非高峰时段开始
2. **可快速回滚** — 每个实验都有 kill switch（立即停止）
3. **有明确的终止条件** — 定义"如果 X 发生，立即停止实验"
4. **事后复盘** — 每个实验的结果都记录为 ADR/evaluation

## 反模式

| 反模式 | 症状 | 修复 |
|--------|------|------|
| **无限重试** | 故障服务被重试压垮，恢复时间延长 | 设置最大重试次数 + 熔断器 |
| **同步重试风暴** | 所有客户端同时重试，形成流量尖峰 | 指数退避 + 抖动 |
| **无超时调用** | 线程永远等待，资源耗尽 | 所有外部调用必须设置超时 |
| **单点降级** | 只有一个降级路径，也失败 | 多级降级（缓存 → 静态 → 拒绝） |
| **无熔断的缓存** | 缓存击穿后流量直达数据库 | 熔断器保护缓存回源 |
| **容错过度** | 隐藏了本应暴露的问题，延迟修复 | 区分"已知故障"和"未知故障" |
| **没有错误预算** | 追求 100% 可用性，无法承受任何发布 | 定义合理的 SLO 和错误预算 |
| **只在测试环境做混沌实验** | 测试环境与生产差异大，实验结果不可信 | 生产环境 + 爆炸半径控制 |

## Rules

1. **Every external call must have a timeout** — 没有超时的外部调用是系统稳定的最大威胁。超时设置：p99 正常延迟 * 2，最小 100ms，最大不超过用户可接受延迟的 50%。

2. **Retry count must not exceed 3** — 超过 3 次的重试说明故障不是瞬时的，继续重试只是增加系统负载。3 次失败后应触发熔断或降级。

3. **Circuit breaker must always have a fallback** — 熔断器打开后必须有明确的降级行为。返回什么？缓存？默认值？队列？不能 "just fail"。

4. **Retries must use exponential backoff with jitter** — 防止所有客户端同步重试形成 traffic spike。Jitter 范围：0-30%。

5. **Critical paths must be resource-isolated from non-critical paths** — 关键业务路径（支付、下单）的线程/连接池必须与辅助路径（日志、监控）隔离。非关键路径的故障不能影响关键路径。

6. **Never depend on a dependency being available at startup** — 服务启动时不应阻塞等待依赖就绪。使用异步初始化 + 健康检查，启动后按需连接。

7. **Define SLO before implementing resilience mechanisms** — 在没有明确可用性目标的情况下设计弹性机制，会导致过度工程或保护不足。

8. **Every resilience mechanism must be tested with chaos experiments** — 熔断器、降级、限流 — 这些机制在代码中存在不等于能按预期工作。必须通过故障注入验证。

## SOP

1. **Phase 1: SLO Definition** — 定义服务的 SLI、SLO 和错误预算。明确"可用"的标准。

2. **Phase 2: Dependency Analysis** — 列出所有外部依赖（数据库、缓存、API、消息队列）。对每个依赖：是强依赖还是弱依赖？故障影响范围？是否有替代方案？

3. **Phase 3: Timeout Configuration** — 为每个外部调用配置超时。基于历史 p99 延迟 * 2 设置。没有历史数据时，使用保守值（500ms-2s）。

4. **Phase 4: Retry Policy Design** — 为可重试的错误类型配置重试策略：最大次数、退避算法、哪些错误码不重试。

5. **Phase 5: Circuit Breaker Setup** — 为每个关键依赖配置熔断器参数：失败阈值、窗口大小、熔断时长、降级行为。

6. **Phase 6: Bulkhead Configuration** — 为关键路径分配独立资源池。确保非关键路径的负载不会影响关键路径。

7. **Phase 7: Load Shedding Design** — 定义过载时的丢弃策略：优先级分层、丢弃阈值、客户端重试协议。

8. **Phase 8: Chaos Testing** — 使用 Chaos Monkey 或类似工具注入故障：kill 依赖、增加延迟、丢包、CPU 饱和。验证降级、熔断和负载丢弃是否按预期工作。

## Checklist

### 防御完整性
- [ ] 所有外部调用有超时配置
- [ ] 所有可重试场景有重试上限
- [ ] 关键依赖有熔断器保护
- [ ] 熔断器有降级策略
- [ ] 关键路径资源隔离
- [ ] 过载时有负载丢弃策略
- [ ] 错误预算和 SLO 已定义

### 故障演练
- [ ] 模拟依赖超时，验证降级行为
- [ ] 模拟依赖不可用，验证熔断触发
- [ ] 模拟高负载，验证限流和负载丢弃
- [ ] 模拟级联故障，验证隔离效果
- [ ] 模拟实例终止，验证自动恢复

## Best Practices

1. **Use the "fail fast" pattern** — 如果知道操作会失败（熔断器打开、必要参数缺失），立即返回错误。不要浪费资源在注定失败的请求上。

2. **Implement graceful degradation as a feature** — 降级不是应急补丁，而是产品设计的一部分。明确哪些功能在降级时可用、哪些不可用、用户会看到什么提示。

3. **Cache fallback data proactively** — 不要只在依赖失败时才想"该返回什么"。在依赖正常时就把响应缓存到本地（或旁路缓存），作为降级时的 fallback。

4. **Design for partial availability** — 系统设计应支持"部分可用"：核心功能始终可用，辅助功能可以降级。不要设计成全有或全无。

5. **Use hedging for read-heavy, latency-sensitive services** — 当服务有多个副本且读操作幂等时，请求对冲可以显著降低尾部延迟。

6. **Practice "defense in depth"** — 弹性不是单一机制，而是多层防线：超时 → 限流 → 熔断 → 降级 → 隔离 → 负载丢弃。每层都是最后一道防线。

## Gotchas

1. **Timeout != Deadline** — Timeout 是单次调用的最大等待时间；Deadline 是整个请求链路的总时间预算。Deadline 必须在整个链路传递，一个慢响应可能耗尽后续所有调用的预算。

2. **Circuit breaker false positives** — 如果窗口太小（如 5 请求），一次正常部署（短暂错误率上升）就可能触发误熔断。窗口至少需要 20-50 请求才有统计意义。

3. **Retry amplification in deep call graphs** — A→B→C 三层调用中，如果每层都重试 3 次，底层 C 实际承受 9x 流量。在深层调用链路中，只允许叶子节点重试。

4. **Bulkhead can starve** — 隔离舱分配的资源如果被一个慢请求占满，其他请求也会被阻塞。配合超时和请求取消，确保资源能被回收。

5. **Load shedding can hide capacity problems** — 负载丢弃解决了症状（系统不崩溃），但没有解决根本原因（容量不足）。告警必须在负载丢弃触发时通知团队。

6. **Gray failures are invisible to aggregate metrics** — 灰度故障下整体指标可能正常，但部分用户受影响。需要节点级、分片级的监控才能发现。

## Context Hints

1. **"Everything fails all the time" (Werner Vogels, AWS CTO)** — 这是设计分布式系统的基本假设。不是"如果失败"，而是"何时失败"。

2. **Spectre of dependencies** — 你依赖的服务比你想象的更脆弱。即使 SLA 是 99.99%，100 个依赖同时存在时，整体可用性 = 0.9999^100 ≈ 99%。任何一个依赖故障都会影响你。

3. **MTBF is less important than MTTR** — 关注平均恢复时间而非平均故障间隔。故障不可避免，关键是快速恢复。自动化降级、自动熔断、自动扩缩容。

4. **Chaos engineering is the only way to validate resilience** — 你无法通过代码审查发现所有弹性缺陷。必须通过在生产环境（或准生产）注入故障来验证。

5. **Resilience mechanisms have failure modes too** — 熔断器自身可能出问题（配置错误、状态机 bug），降级逻辑可能引入新 bug。弹性代码也需要测试。

6. **The best resilience is simplicity** — 简单的架构（少依赖、少状态共享、清晰的故障边界）比复杂的容错代码更可靠。复杂性是弹性的敌人。
