# 代码模块化与重构

> **使用场景**：评估模块拆分时机、识别代码异味、规划安全重构路径、评审模块边界时加载本 skill

## 第一性原理

> **模块化的本质**：通过信息隐藏和职责分离，将系统分解为可独立理解、测试、修改的单元，使变更的 blast radius 最小化。

---

## 何时拆分模块

### 拆分触发信号

| 信号 | 严重程度 | 说明 |
|------|---------|------|
| **代码行数 > 600** | 🔴 高 | 单文件超过 600 行，认知负荷过大 |
| **修改频率高 + 冲突多** | 🔴 高 | 多个团队/开发者频繁修改同一文件 |
| **职责不单一** | 🔴 高 | 无法一句话描述模块职责 |
| **循环依赖** | 🔴 高 | A→B→C→A，架构耦合 |
| **测试困难** | 🟡 中 | 需要启动大量依赖才能测试一个小功能 |
| **复用受阻** | 🟡 中 | 想复用部分功能，但必须引入整个模块 |
| **编译/构建慢** | 🟡 中 | 小修改触发大范围重编译 |
| **命名宽泛** | 🟢 低 | `utils`, `helpers`, `common` 等模糊命名 |

### 拆分决策矩阵

| 指标 | 拆分（提取新模块） | 合并（简化模块） |
|------|-----------------|----------------|
| **耦合度** | 与单一外部模块高耦合 | 与多个模块松散耦合 |
| **内聚度** | 内部多组无关功能 | 所有功能紧密相关 |
| **变更模式** | 不同功能独立变更 | 功能总是一起变更 |
| **复用需求** | 部分功能被多模块复用 | 无复用需求 |
| **团队结构** | 多个团队维护不同子功能 | 单一团队维护 |

**规则**：当 **(高耦合 + 低内聚 + 独立变更)** 时，必须拆分。

## 何时不要拆分

**过度拆分的代价**：

| 问题 | 症状 |
|------|------|
| **接口爆炸** | 每个小模块都需要接口文件，接口数量 > 模块数量 |
| **调用链过长** | A→B→C→D→E 完成一个简单操作 |
| **数据转换开销** | 每个边界都需要 DTO 转换 |
| **发布协调成本** | 修改涉及 5 个模块的同步发布 |
| **认知碎片** | 理解一个功能需要打开 10 个文件 |

**合并信号**：
1. 两个模块总是一起变更（commit 历史高度相关）
2. 模块间调用是 1:1（无复用）
3. 接口 overhead 超过业务逻辑本身

## 代码异味识别

### 架构级异味

| 异味 | 检测方法 | 风险 |
|------|---------|------|
| **God Module** | > 600 行，> 30 个导出 | 变更影响不可预测 |
| **Feature Envy** | 方法大量操作其他模块数据 | 应移动到数据所在模块 |
| **Shotgun Surgery** | 改一个功能要改 N 个文件 | 逻辑分散，易遗漏 |
| **Divergent Change** | 一个模块因多种原因变更 | 职责不单一 |
| **Cyclic Dependency** | 模块间循环 import/require | 无法独立测试/理解 |

### 代码级异味

| 异味 | 检测方法 | 修复 |
|------|---------|------|
| **Long Function** | > 50 行 | 提取策略/工具函数 |
| **Large Class** | > 200 行 | 拆分为多个类 |
| **Primitive Obsession** | 用原始类型表达领域概念 | 引入值对象 |
| **Data Clump** | 相同 3+ 参数频繁一起出现 | 封装为对象 |
| **Switch Statements** | 重复 switch/case | 策略模式/多态 |

## 安全重构路径

### 重构优先级

```
1. 低风险 + 高影响 → 立即做
2. 低风险 + 低影响 → 顺手做
3. 高风险 + 高影响 → 计划做（充分测试）
4. 高风险 + 低影响 → 不要做
```

### 安全重构 checklist

| 步骤 | 必须做的事 |
|------|----------|
| **1. 确保测试覆盖** | 重构前目标代码覆盖率 ≥ 70%，关键路径 100% |
| **2. 小步提交** | 每次重构一个单一变换，一次 commit |
| **3. 行为不变** | 重构前后输出完全一致（ refactoring ≠ 改功能） |
| **4. 验证每步** | 每步后运行测试，失败立即回滚 |
| **5. 代码审查** | 重构后必须有他人 review |

### 推荐的重构顺序

1. **先补测试** — 没有测试覆盖的重构是赌博
2. **提取函数** — 将长函数拆分为命名良好的小函数（最安全）
3. **提取类/模块** — 将相关函数和数据封装到新类
4. **消除重复** — 合并相似代码（提取公共函数）
5. **简化接口** — 减少参数、消除不必要的间接层
6. **打破循环依赖** — 引入接口/抽象层

## 模块化设计原则

### 信息隐藏层级

| 层级 | 可见性 | 例子 |
|------|--------|------|
| **私有** | 模块内部 | 内部数据结构、辅助函数 |
| **包/模块级** | 同模块内 | 模块内部共享的工具 |
| **公开** | 所有消费者 | 稳定的 API 接口 |
| **已废弃** | 仍可见但标记废弃 | 将在下版本移除的接口 |

### 接口稳定性评估

| 接口特征 | 稳定性 | 使用建议 |
|---------|--------|---------|
| 功能已被多个模块使用 | 高 | 谨慎修改，需废弃周期 |
| 仅内部使用 | 中 | 可修改，但需内部同步 |
| 刚创建、未使用 | 低 | 可自由修改 |

## 反模式

| 反模式 | 症状 | 修复 |
|--------|------|------|
| **Big Bang Refactoring** | 一次性重构 5000 行代码 | 拆分为小步，每步可独立验证 |
| **Refactoring without tests** | "我确信改动是正确的" | 先写测试，再重构 |
| **Copy-paste refactoring** | 拆分时复制代码，未消除重复 | 提取公共代码到共享位置 |
| **Over-engineered abstraction** | 为 2 个用例创建抽象层 | 遵循 Rule of Three |
| **Module fan-in/fan-out imbalance** | 一个模块被 20 个模块依赖 | 考虑拆分为更细粒度的接口 |

## Rules

1. **Never refactor without tests** — 没有测试的重构是重写。重构必须保证行为不变，而只有测试能验证行为不变。

2. **One transformation per commit** — 每次 commit 只做一种重构：提取函数、重命名、移动文件。混合多种重构导致回滚困难。

3. **Extract first, abstract later** — 先提取具体实现，看到 3 个具体用例后再抽象。Rule of Three：抽象前至少看到 3 个实例。

4. **Module boundaries must match team boundaries** — 如果一个模块需要两个团队频繁协调，边界就错了。模块边界应使一个团队能独立工作。

5. **Public API is a commitment** — 公开的接口是契约。修改公开接口的成本远高于修改私有实现。减少公开接口数量，增加私有实现自由度。

6. **Prefer duplication over wrong abstraction** — 错误的抽象比重复制代码更难修复（Sandi Metz）。不确定时，先复制；看到明确模式后，再提取。

## SOP

1. **Phase 1: Identify Target** — 使用代码异味清单识别需要重构的模块。量化：代码行数、复杂度指标（cyclomatic complexity）、变更频率。

2. **Phase 2: Build Safety Net** — 为待重构代码编写测试。目标：覆盖所有公开接口和关键路径。没有测试覆盖不开始重构。

3. **Phase 3: Small-Step Refactoring** — 每次只做一种重构变换：提取函数、内联变量、移动方法、重命名。每步后运行全部测试。

4. **Phase 4: Extract Module** — 当提取的函数形成内聚集合时，创建新模块。定义清晰的公开接口，隐藏实现细节。

5. **Phase 5: Verify & Review** — 重构完成后：运行全部测试通过、进行代码审查、更新依赖文档。

6. **Phase 6: Monitor** — 重构后观察生产指标：错误率、性能、日志异常。确保重构没有引入回归。

## Checklist

### 重构前
- [ ] 目标代码有 ≥ 70% 测试覆盖
- [ ] 关键路径有 100% 测试覆盖
- [ ] 测试在重构前全部通过
- [ ] 重构范围已明确（不改功能）

### 重构中
- [ ] 每次只做一个变换
- [ ] 每步后运行测试
- [ ] 测试失败时立即回滚
- [ ] 小步提交（频繁 commit）

### 重构后
- [ ] 全部测试通过
- [ ] 代码审查完成
- [ ] 无功能变更（行为一致）
- [ ] 接口文档已更新
- [ ] 生产指标监控已配置

## Best Practices

1. **Use "Move Method" to fix Feature Envy** — 如果一个方法大量操作另一个类的数据，把它移动到那个类。这是最低风险的重构之一。

2. **Create "seams" for testing before refactoring** — 在重构前为不可测试的代码创建 seam（注入点）。例如，将 `new Database()` 改为通过参数传入。这使代码可测试，同时不改变行为。

3. **Document why, not what, when deprecating** — 废弃接口时，文档说明：为什么废弃？替代方案是什么？何时删除？不要只写 "deprecated"。

4. **Refactor during feature work, not as separate projects** — 最好的重构时机是修改相关功能时。"重构周"或"重构项目"往往被其他优先级挤占。顺带重构（boy scout rule）：离开营地时比来时更干净。

## Gotchas

1. **Extracting a module creates a new dependency** — 拆分的模块需要被原模块依赖。确保新模块的依赖方向正确（不要反向依赖）。如果拆分导致循环依赖，说明拆分时机或方式不对。

2. **Common module becomes a dumping ground** — `common`, `utils`, `shared` 模块会自然成为垃圾场。设定明确的准入标准：什么可以进？什么不可以？定期清理。

3. **Module extraction changes build system** — 拆分为独立模块可能触发构建配置变更（webpack、rollup、TypeScript project references）。评估构建复杂度增加是否值得。

4. **Refactoring and feature changes don't mix** — 同一个 PR 中既重构代码又添加功能，review 极为困难。如果必须同时做，拆分为两个 commit：先重构（行为不变），后添加功能。

## Context Hints

1. **Code is read 10x more than written** — 你的代码将被阅读的次数远多于编写的次数。优化代码的可理解性比重构时的便利性更重要。

2. **"Write code that's easy to delete, not easy to extend"** — 可删除性（deletability）是模块化的终极指标。如果一个模块可以被删除而不需要修改其他 20 个文件，它就是好的模块化。

3. **The "Strangler Fig" pattern for large-scale refactoring** — 不要一次性重写大模块。创建新模块，逐步将流量/调用从老模块迁移到新模块，最后删除老模块。这和重写不同，因为它始终有可工作的系统。

4. **Conway's Law: your code structure mirrors your org structure** — 如果你强行拆分了模块，但团队仍然作为一个整体工作，模块边界会被绕过（通过共享代码、直接访问内部）。模块结构必须与团队结构对齐。
