# 技术决策与选型

> **使用场景**：面临技术选型、框架迁移、引入新依赖、升级vs重写等决策时加载本 skill

## 第一性原理

> **技术决策的本质**：在约束条件（时间、人力、风险容忍度）下，选择能最大化业务价值交付的技术路径，而非追求技术完美。

---

## 决策前置检查

在做出任何技术决策前，**必须回答**：

| 问题 | 为什么重要 |
|------|-----------|
| **业务目标是什么？** | 技术服务于业务，不了解业务目标的技术决策是无源之水 |
| **约束条件有哪些？** | 时间、预算、团队技能、合规要求等硬约束 |
| **不选的代价是什么？** | 维持现状的成本 vs 变更的成本 |
| **回滚方案是什么？** | 每个决策都可能是错的，必须有退路 |

> 如果以上问题不清晰，不要做决定。先澄清需求。

## 决策矩阵框架

### 维度定义

| 维度 | 权重建议 | 评估要点 |
|------|---------|---------|
| **业务匹配度** | 25% | 是否直接解决业务痛点？ROI 如何？ |
| **团队能力** | 20% | 团队现有技能栈？学习曲线？维护能力？ |
| **生态成熟度** | 15% | 社区活跃度？文档质量？长期维护承诺？ |
| **性能 & 扩展性** | 15% | 是否满足当前及未来 2-3 年的性能需求？ |
| **运维复杂度** | 15% | 部署复杂度？监控难度？故障排查成本？ |
| **迁移成本** | 10% | 数据迁移？代码重写？兼容性风险？ |

### 评分规则

每个维度按 1-5 分评分：
- **5分**: 显著优于现状，几乎无风险
- **4分**: 优于现状，风险可控
- **3分**: 与现状持平
- **2分**: 存在明显缺陷或风险
- **1分**: 重大风险，不建议采用

计算加权总分，**总分 < 3.0 的方案直接淘汰**。

## ROI 量化评估框架

技术决策不能只停留在"感觉好"或"感觉差"。必须量化。

### TCO（总拥有成本）公式

```
TCO = 引入成本 + 学习成本 + 维护成本 + 迁移成本 - 收益现值

引入成本  = 开发人时 × 时薪 × 1.5（含测试+review）
学习成本  = 团队人数 × 预计学习天数 × 日薪 × 0.5（并行学习效率）
维护成本  = 年运维人天 × 3年（技术栈平均生命周期）× 日薪
迁移成本  = 数据迁移人时 + 兼容性改造人时 + 回退方案预备人时
收益现值  = Σ(年收益增量 / (1 + 折现率)^年)
```

**决策规则**：
- TCO < 0：净收益为负，除非战略需要，否则不做
- TCO 在 0-6个月回本：绿灯，快速推进
- TCO 6-12个月回本：黄灯，需要额外业务价值论证
- TCO > 12个月回本：红灯，除非战略级决策

### 机会成本计算

不决策也有成本——拖延的代价：

```
机会成本 = 当前问题造成的损失/月 × 预计等待月数
```

**规则**：如果（解决问题的月收益 × 6个月）> TCO，决策不应拖延超过2周。

### 沉没成本谬误识别

| 错误推理 | 正确视角 |
|---------|---------|
| "已经在旧框架上投入 2000 人时，不能换" | 过去的投入是沉没成本，决策只看未来增量 |
| "团队刚学会这个，换太浪费" | 学习成本已在 TCO 中量化，不应重复计算 |
| "重写需要重新测试所有功能" | 测试也应在 TCO 中量化，不能因为它是"已知成本"就忽略 |

## 升级 vs 重写 决策算法

| 指标 | 量化方法 | 升级阈值 | 重写阈值 |
|------|---------|---------|---------|
| **代码质量** | 圈复杂度均值 | < 15 | > 25 |
| **测试覆盖** | 行覆盖率 | > 60% | < 30% |
| **业务逻辑清晰度** | 新成员理解核心流程所需天数 | < 3天 | > 7天 |
| **技术债密度** | TODO/FIXME 数量 / 代码行数 | < 0.5% | > 2% |
| **依赖健康状况** | 关键依赖最后更新时间 | < 6个月 | > 2年 |

### 决策公式

```
重构成本指数 RCI = (重写人时 / 维护人年 × 3)

如果 RCI < 2.0：升级（逐步重构）
如果 2.0 ≤ RCI ≤ 4.0：混合策略（Strangler Fig 模式）
如果 RCI > 4.0：重写
```

**关键假设验证**（重写前必须确认）：
1. 业务规则已完全文档化或可被核心团队复述
2. 新架构方案经过 PoC 验证（至少覆盖20%最复杂场景）
3. 有至少2个月的连续工程窗口

## 架构熵评估

技术决策的累积效果可以用"架构熵"来度量——系统混乱程度的趋势。

### 熵增信号

| 信号 | 检测方法 | 熵值 |
|------|---------|------|
| 循环依赖数量 | `grep` cross-module imports | 每个循环依赖 +5 |
| 无注释的 hack/TODO | 代码扫描 | 每个 +1 |
| 未经评审的技术引入 | 决策记录缺失 | 每次 +10 |
| 单文件行数超标 | 超过架构约束 | 每个 +3 |
| 测试覆盖率下降 | 月环比 | 每下降 5% +5 |

### 熵减策略

```
每月熵减目标 = 上月熵值 × 0.1（每月减少10%）
```

**规则**：当熵值超过项目启动时的 2 倍时，必须安排专门的技术债清理迭代。

## 技术雷达定位与四象限决策

使用 ThoughtWorks Tech Radar 的四象限模型评估技术：

| 象限 | 策略 | 进入条件 | 退出条件 |
|------|------|---------|---------|
| **Adopt（采用）** | 可在生产环境放心使用 | 团队内部有2个以上成功生产案例 | 出现更优替代且迁移成本可接受 |
| **Trial（试用）** | 先在非关键系统试点 | 社区成熟度中等，有初步成功案例 | 试点失败或Adopt条件满足 |
| **Assess（评估）** | 保持关注，暂不投入 | 新兴技术，潜在价值但案例不足 | 被替代或进入Trial |
| **Hold（暂缓）** | 避免使用 | 已被替代、社区衰退或已知重大缺陷 | 重新评估后进入Assess |

**规则**：生产环境核心路径只使用 **Adopt** 级别技术；**Trial** 技术只允许在隔离环境中使用。

### 技术的生命周期意识

每项技术都有生命周期曲线：

```
创新触发 → 期望膨胀 → 幻灭低谷 → 复苏爬坡 → 生产成熟期 → 衰退期
   ↑              ↑           ↑            ↑            ↑          ↑
 Assess         Trial       Assess      Trial→Adopt   Adopt      Hold
```

> 在"期望膨胀期"引入技术 = 高风险。在"复苏爬坡"早期引入 = 最大竞争优势。

## 决策时机与博弈论

技术决策往往不是纯技术问题，而是多方利益的博弈。

### 利益相关方分析

| 角色 | 关注点 | 典型立场 | 说服策略 |
|------|-------|---------|---------|
| **CTO/架构师** | 长期技术健康 | 可能偏保守或偏激进 | 用架构熵数据和TCO量化 |
| **产品经理** | 交付速度 | 反对任何延迟 | 强调决策拖延的月成本 |
| **运维/SRE** | 稳定性 | 反对新引入的不确定因素 | 提供回滚方案+灰度计划 |
| **安全团队** | 合规与风险 | 对未知技术警惕 | 提供安全审计报告 |
| **一线开发者** | 开发体验 | 偏好熟悉或酷炫的技术 | 用PoC实际体验说服 |

### 冲突决策策略

当利益冲突时：

1. **数据优先**：用量化指标（TCO、熵值、性能基准）替代主观争论
2. **时间盒决策**：设定决策截止日期（通常2周），避免分析瘫痪
3. **分阶段承诺**：用 PoC → 试点 → 全面推广的三阶段降低各方风险
4. **可逆性优先**：选择容易回滚的方案作为共识基础

### 决策拖延的成本

```
每月拖延成本 = (当前问题的业务影响/月) + (机会成本) + (团队士气衰减)
```

> 如果每月拖延成本 > TCO 的 10%，任何超过 2 周的拖延都是组织失败。

## 常见决策场景

### 场景1：框架/库选型

| 考量因素 | 关键问题 |
|---------|---------|
| **功能覆盖度** | 核心需求是否全部覆盖？边缘需求是否可妥协？ |
| **API 稳定性** | SemVer 合规？破坏性变更频率？ |
| **Bundle 大小** | 对前端：增加多少 KB？对后端：启动时间影响？ |
| **许可协议** | MIT/Apache vs GPL/商业许可——法务风险 |

**决策规则**：
1. 优先选择 **团队已有经验** 的技术（降低认知负荷）
2. 引入新技术须有 **明确痛点**（现有方案确实无法满足）
3. 新技术须经过 **PoC 验证**（概念验证，至少覆盖核心场景）

### 场景2：升级 vs 重写

| 指标 | 选择升级 | 选择重写 |
|------|---------|---------|
| **代码质量** | 结构尚可，主要问题是技术债 | 架构腐烂，无法局部修复 |
| **业务逻辑复杂度** | 业务规则已验证，变更风险低 | 业务规则清晰，重新实现可控 |
| **团队熟悉度** | 团队理解现有代码 | 现有代码无人理解 |
| **时间压力** | 有连续交付压力 | 有窗口期允许暂停新功能 |
| **测试覆盖** | 有合理测试覆盖 | 测试缺失，但可接受重建 |

**核心原则**：
> 重写是最后手段。当且仅当 **(维护成本 > 重写成本) AND (业务逻辑清晰可重建)** 时才考虑重写。

### 场景3：自建 vs 购买/第三方

| 考量 | 自建 | 第三方 |
|------|------|--------|
| **核心竞争力** | 属于核心差异化能力 | 通用能力，非差异化 |
| **定制化需求** | 需要深度定制 | 标准功能即可满足 |
| **控制度** | 需要完全控制 | 可接受供应商锁定风险 |
| **维护成本** | 团队长期维护 | 外包维护成本 |

**规则**：非核心能力优先使用成熟的第三方方案；核心能力必须自建以保持竞争力。

### 场景4：同步 vs 异步架构

| 场景 | 推荐 | 理由 |
|------|------|------|
| 用户等待的响应 | 同步 | 用户需要即时结果 |
| 耗时 > 500ms 的操作 | 异步 | 避免阻塞用户请求 |
| 跨服务写操作 | 异步（事件驱动） | 降低耦合，提高可用性 |
| 强一致性要求 | 同步 + 事务 | 最终一致无法满足业务 |
| 高吞吐批量处理 | 异步 + 队列 | 削峰填谷，保护下游 |

## 反模式

| 反模式 | 症状 | 修复 |
|--------|------|------|
| **简历驱动开发** | 选择新技术只为学习而非业务需要 | 回归业务目标，量化 ROI |
| **大厂崇拜** | "Google 用 X 所以我们也要用 X" | 评估自身规模与约束，Google 的问题不是你的问题 |
| **早期优化** | 为想象中的未来需求选择复杂方案 | YAGNI——为最可能发生的场景设计 |
| **分析瘫痪** | 过度比较，迟迟不做决定 | 设定决策时限，收集 80% 信息即决策 |
| **技术孤岛** | 不同团队各自选型，无统一标准 | 建立技术委员会，制定准入标准 |
| **沉没成本绑架** | "已经投入太多，不能换" | 用增量分析：只看未来成本收益 |
| **追逐最新版本** | 每个小版本更新都立即跟进 | 建立版本升级节奏（如季度评估），区分安全补丁和功能升级 |

## Rules

1. **Every technology decision must have a documented rationale** — 记录决策上下文、约束条件、考虑过 alternatives、最终选择及原因。无记录的决策 = 未来的技术债。

2. **Prefer proven over novel in production** — 生产环境优先选择成熟稳定的技术。新技术只能在非关键路径或隔离环境中试用。

3. **PoC before commitment** — 任何引入新技术的决策前，必须先做概念验证（Proof of Concept）。PoC 必须覆盖：核心功能验证、性能基准、团队学习成本评估。

4. **Estimate total cost of ownership, not just adoption cost** — 评估技术的总拥有成本：学习成本 + 开发成本 + 维护成本 + 迁移成本。仅看引入成本会导致严重低估。

5. **Design for reversibility** — 优先选择容易回滚或替换的方案。如果两个方案功能相近，选择耦合度更低、更容易迁移的那个。

6. **Align technology choices with team capabilities** — 选择团队能在 2 周内上手的技术。再优秀的技术，如果团队无法有效维护，也是错误选择。

7. **Time-box every decision to 2 weeks maximum** — 拖延超过2周的技术决策，其机会成本通常已超过决策本身的收益。设定硬截止日期。

8. **Never make decisions based on sunk cost** — 过去的投入不可回收。评估技术方案时只看未来的增量成本和增量收益。

## SOP

1. **Phase 1: Context Clarification** — 明确业务目标、约束条件、成功标准和失败标准。收集 stakeholders 的输入。

2. **Phase 2: Alternative Identification** — 列出至少 2-3 个可行方案（包括维持现状）。对每个方案，收集：功能覆盖、生态成熟度、性能数据、许可信息。

3. **Phase 3: Structured Evaluation** — 使用决策矩阵对每个方案评分。权重可根据项目调整，但必须文档化调整理由。

4. **Phase 4: ROI Quantification** — 计算每个方案的 TCO 和机会成本。量化拖延的月成本。

5. **Phase 5: Risk Assessment** — 对每个高分方案进行风险分析：最坏情况是什么？发生概率？缓解措施？回滚方案？

6. **Phase 6: Decision Documentation** — 编写 ADR（Architecture Decision Record）：上下文、决策、影响、alternatives considered、回滚计划。

7. **Phase 7: Validation** — 对选定方案进行 PoC 验证。如果 PoC 失败，返回 Phase 2。

## Best Practices

1. **Use the "Rule of Two" for technology diversity** — 同一类别技术不要超过 2 种（如 2 种数据库、2 种缓存）。技术多样性增加运维复杂度和认知负荷。

2. **Create a "decision log" for each major technology choice** — 不是正式的 ADR，而是一个简单的表格：日期、决策、原因、决策人。帮助未来团队理解历史选择。

3. **Revisit technology decisions quarterly** — 技术生态变化快。每季度回顾一次关键技术决策：still valid? 是否有更好的 alternatives? 是否到了迁移窗口?

4. **Start with the team you have, not the team you want** — 不要基于"招到专家后"做决策。基于当前团队的能力选择技术，然后通过培训提升能力。

5. **Calculate "decision fatigue" when multiple choices coexist** — 当同时面临多个技术决策时，按业务影响排序，一次只做一个重大决策。多个并行技术决策的出错率指数级增长。

## Gotchas

1. **Open source sustainability crisis** — 很多流行的开源项目由 1-2 人维护，没有可持续的资助模式。评估技术时检查：核心维护者数量、最近 commit 频率、是否有商业支持选项。

2. **Vendor lock-in in "open" standards** — 某些"开放标准"实际上由单一厂商控制。评估时检查：标准是否有多个独立实现？治理模式是否透明？

3. **Performance benchmarks are usually lies** — 厂商提供的 benchmark 通常经过优化，不代表真实场景。总是用自己的 workload 做基准测试。

4. **"Free" open source has hidden costs** — 没有商业支持的 OSS 意味着你自己就是支持团队。计算：issue 响应时间、security patch 跟进成本、升级成本。

5. **Version compatibility traps** — 升级一个依赖可能触发整个依赖树的兼容性重评估。使用 `npm ls`（或等效工具）检查传递依赖的健康状况，避免"升级一个包，破碎整个系统"。

## Context Hints

1. **Conway's Law applies to technology choices too** — 如果组织有两个独立团队，他们自然会选择不同的技术栈。统一技术栈需要组织调整，不能仅靠技术规定。

2. **The "best" technology is the one your team can ship with** —  shipped code beats perfect architecture。一个在 2 周内用熟悉技术交付的方案，优于 2 个月用新技术但延迟交付的方案。

3. **Technology decisions compound** — 今天选择的技术栈会影响未来 3-5 年的所有决策。一个早期的错误选择会产生连锁反应，修正成本随时间指数增长。

4. **"Not inventing here" is as dangerous as "not invented here"** — 盲目自建和盲目外采都是问题。核心能力自建，通用能力外采，边界随时间演进。

5. **Decide at the last responsible moment** — 不是延迟决策，而是在信息充分但不完美的时刻决策。过早决定 = 基于不完整信息的赌博；过晚决定 = 机会成本累积。
